# 浏览器标签页会话管理器对比

> [!abstract] 适用场景
> 需要找一个能替代 Tab Session Manager（TSM）的浏览器扩展：要有**命名会话库**、
> 云同步可靠、Firefox 与 Chromium 双支持、且开源。
> 这篇横向对比十余个候选，给出首选/次选方案、排除理由、迁移路径与移动端约束。
> 读完可以在 NiceTab 与 Konode 两条路线之间做出取舍，并知道各自的同步语义差异
> （NiceTab 有会话库但"删除不传播"；Konode 同步更可靠但没有会话库）。

## 1 背景与适用条件

**Tab Session Manager（TSM）** 是 Firefox/Chromium 上的标签会话管理器，把当前窗口的标签
保存为可命名的会话库，之后按需恢复。其云同步基于 Google Drive 的隐藏 `appDataFolder`
空间，官方 UI 自己标注为 **"Enable cloud sync (Beta)"**，是本篇调研的替换动机。

- TSM 仓库：<https://github.com/sienori/Tab-Session-Manager>
- NiceTab 仓库：<https://github.com/web-dahuyou/NiceTab>
- Konode 仓库：<https://github.com/konabe-studio/konode>
- floccus 仓库：<https://github.com/floccusaddon/floccus>

**需求口径（2026-10-01 确认）**：书签同步继续用 **floccus**（不动），本篇只解决
**标签/会话同步**。即要找的是「和 TSM 一样有**命名会话库** + 云同步可靠 +
Firefox/Chromium 双支持 + 开源」的方案。

**三条硬约束**：

1. **云同步可用且可靠** —— 换掉 TSM 的直接动机就是它的云同步难用；
2. **Firefox 与 Chromium 都要支持**；
3. **开源**。

**版本敏感性**：所有版本号、用户数、评分、源码行号均为 **2026-10-01** 的快照。
扩展更新频繁，以下结论基于该日期，更新版本可能变化。

**前置条件**：能访问 Firefox AMO / Chrome Web Store / Edge 商店安装扩展；
若选 WebDAV 或 GitHub/Gitee Gists 后端，需要自备对应账户与凭据。

**适用范围**：桌面浏览器（Firefox / Chromium 系）的标签会话管理扩展选型。
**不适用**：移动端浏览器（见 §8，平台限制导致扩展路线到不了手机）；
只想同步**书签**而非会话的场景（继续用 floccus 即可）。

> 数据来源均为一手：GitHub API / raw.githubusercontent.com 源码、AMO API v5、Chrome Web Store 与 Edge 商店页面、项目自带 README/ROADMAP/CHANGELOG/PRIVACY。凡未能一手证实的一律标 **UNVERIFIED**。

## 2 结论速览

**没有单一扩展能同时在「云同步可靠」「双浏览器」「开源」三项上与 TSM 功能完全对等。** 需要在两个方向里选一个：

| 方案 | 一句话 | 适合谁 |
|---|---|---|
| **A. NiceTab**（首推） | **唯一满足「命名会话库 + 自有后端同步 + 双浏览器 + 开源」**：`Category > Tab Group > Tab` 存成可命名的会话组长期保存，同步到 WebDAV（多账户）或 GitHub/Gitee Gists | 要**标签会话**本身（= TSM 用法），接受同步是"merge 推送、删除不自动传播"，需要时手动 force overwrite |
| **B. Konode**（次推） | 同步可靠性最好（删除感知合并 + 多设备收敛 + 可选 E2EE + 三个自有后端），但**没有会话库** | 更看重**同步可靠/隐私**，且能接受"只有每设备当前那组标签、无历史会话库" |
| C. floccus tabs | 不推荐——tabs 模式官方自称实验性（"sometimes causes tabs to duplicate"），auto-push 有覆盖风险，且不是会话库 | 仅当只想要"换设备接着开当前标签" |
| D. 自托管 KeepSync | **已排除**，见 §9 | — |

**关键取舍一句话**：**NiceTab 有会话库但同步"删除不传播"**（默认 merge 推送是并集，删除会被别的设备推回来、标签累积增长，需本地删完手动 force push 覆盖）；**Konode 同步更靠谱但没有会话库**（session = 每设备当前打开的那组标签，popup 里按设备列出并一键恢复，且**不能导入 TSM 数据**）。要标签会话 → **NiceTab**。详见 §5、§6。

## 3 为什么要换：TSM 现状

| 项 | 值 |
|---|---|
| AMO 用户 | **164,500** |
| AMO 评分 | **4.16 / 5**（1,239 条） |
| 当前版本 | 7.4.0（文件日期 2026-07-17） |
| 许可证 | MPL-2.0 |
| Open issues/PR | **681** |

云同步实现（源码核实）：走 Google Drive 的隐藏 `appDataFolder` 空间（`cloudAPIs.js` 里 `spaces: "appDataFolder"`），OAuth scope 恰为 `drive.appfolder` + `userinfo.email`；冲突解决是**逐文件 LWW**（按 `lastEditedTime`）；auto-sync 只在浏览器启动 / 保存会话时触发并做 10 秒 debounce；失败时置 `signInRequired` 并显示红色徽章。UI 上这个功能自己标着 **"Enable cloud sync (Beta)"**。

顺手核实的两条 TSM 事实（与迁移相关）：

- **备份导出**（`src/background/backup.js`）由 `backupSessions` alarm 驱动（onStartup 时 `delayInMinutes: 0.5`），增量导出自 `lastBackupTime` 以来有改动的会话；默认 `ifBackup` 为 **false**。UI 原文："The save location is limited to the folder under browser download"。
- **没有自动导入**：`src/background/import.js` 的 `importSessions()` 只由用户消息 `{message:"import"}` 触发，全树无 file watcher、无定时导入。
- 平台硬限制（MDN browser-compat-data）：File System Access API 的 `showSaveFilePicker`/`showDirectoryPicker` 在 **Firefox 为 false**，且要求 "Transient user activation is required"；扩展唯一无人值守写路径 `downloads.download` 的 `filename` 只能是"default downloads directory 下的相对路径"，绝对路径与 `../` 直接报错。**所以任何扩展都无法静默读写任意同步目录，文件同步路线只能半手动。**

## 5 方案 A：NiceTab（首推）——唯一满足「命名会话库 + 自有后端同步 + 双浏览器 + 开源」

<https://github.com/web-dahuyou/NiceTab> · AMO <https://addons.mozilla.org/en-US/firefox/addon/nice-tab-manager/> · CWS `fonflmjnjbkigocpoommgmhljdpljain` · Edge `ompjiaelpibiggcnanhbdblkhfdmkgnl`

**是什么**：GPL-3.0，WXT + TypeScript，764★/86 forks，pushed 2026-09-28。README 定位原文：OneTab、Toby、N-Tab、SessionBuddy、KepTab 的升级替代品，"supports browsers such as Chrome, Firefox, Microsoft Edge, and any Chromium based browser"。

### 5.1 为什么它最像 TSM

数据模型是 **`Category > Tab Group > Tab`** 三层（GUIDE.md）。你把当前窗口（或所有窗口）的标签一键送进列表，成为可**命名、长期保存**的 tab group，之后按组恢复。这正是 TSM "保存命名会话库"的使用感，而 Konode 没有。

支持 NiceTab / OneTab / Toby / SessionBuddy / KepTab 格式导入（README L50、L121-122）——**但不含 TSM 格式**。

### 5.2 同步

- **双后端**：**Gists**（GitHub 或 Gitee，PAT 只需 `gists` scope）与 **WebDAV**（URL + 用户名 + 密码，**支持多个 WebDAV 账户**）。
- 同步对象含 **tab list 和 preferences**。
- **Auto Sync** 可开关、可设频率与方式。
- 源码核实（`entrypoints/common/constants.ts:289-300`）：同步方式是 8 种组合——`{AUTO,MANUAL}_{PULL,PUSH}_{MERGE,FORCE}`，默认 `auto-push-merge`；`autoSyncAlarm.ts` 用 `periodInMinutes` 定时（默认 30 分钟，可切小时单位）。`MANUAL_PULL_FORCE` / `AUTO_PULL_FORCE` 会先 `clearAll()` 再整体覆盖；`_PUSH_FORCE` 会先 `backupRemoteData()` 再覆盖。
- 同步文件名固定为 `__NiceTab_gist__.json` 与 `__NiceTab_settings_gist__.json`。

### 5.3 ⚠️ 主要扣分项：删除不传播

README L85 与 L135 两处原文警告：

> "note that merging push do not perform a diff-comparison delete; it merges remote and local, then pushes to remote. **To sync deletions, remove them locally and then manually overwrite the remote.**"

即默认的 merge 推送是**并集**，不是 diff——你在 A 设备删掉的东西会被 B 设备推回来，标签会**累积增长**。要真删除必须本地删完再手动 force overwrite 远端。这和 Konode 的 tombstone 删除感知合并是本质差距。

其他：中文社区项目（README/GUIDE 有 en/zh/ru 版本，界面 i18n 含 enUS/zhCN/zhTW/ruRU）；AMO 仅 **95 用户**；CWS 4.2。

## 6 方案 B：Konode（次推）——同步更可靠，但没有会话库

<https://github.com/konabe-studio/konode> · AMO <https://addons.mozilla.org/en-US/firefox/addon/konode/> · CWS <https://chromewebstore.google.com/detail/konode/mmlfiiimnpnjcjhhbldenpcmnibedkfa>

**是什么**：MPL-2.0，TypeScript，MV3。README 定位原文："Sync your browser to storage you own: no middleman, no account, no tracking." **没有 Konode 服务器、没有账号、没有遥测**——扩展只是"管道的两端"，把数据直接写进你自己选的后端。

### 6.1 同步什么

| 数据类型 | 默认 | 说明 |
|---|---|---|
| 书签 | **开** | 双向、保留文件夹结构、**删除会传播**（tombstone） |
| Open tabs / sessions | opt-in | "Save the current tab set and restore another device's session whenever you want." |
| 浏览历史 | opt-in | 默认只读近 **30 天**、每次 sync 至多 **5,000** 页，排除 `file://` 与浏览器内部页 |
| 已装扩展列表 | opt-in | **只读**，不能安装/移除/启用/禁用 |

### 6.2 后端与加密

- 三选一：**Google Drive**（scope 仅 `drive.file`）、**GitHub**（fine-grained PAT + 一个私有仓库）、**WebDAV**（预设 Nextcloud/ownCloud、pCloud、Koofr、Fastmail、坚果云，以及 "WebDAV (other)" 覆盖 Synology/kDrive/任意标准 WebDAV）。Mega 仅标 "Planned"。
- **可选 E2EE**：AES-256-GCM + PBKDF2-SHA256 **600k** 轮，默认**关闭**且必须显式开启，口令 ≥12 字符或生成密钥；每个 payload 带 SHA-256 校验和并在下载后校验。
- 凭据只存 `storage.local`。

### 6.3 同步机制（这才是它比 TSM 强的地方）

- 每设备每类型写一个 `konode_<type>_<device_id>.json` 到后端的 `konode/` 目录（每个后端一个目录）。
- 每次 sync：拉取**所有** peer 文件 → **非破坏性合并** → 回推。3+ 设备也能收敛，**不需要中心服务器**。
- 书签用 tombstone 让删除传播，并有安全上限防止损坏的删除日志清空书签树（`Max bulk delete from a peer`，默认 60%，可调 50–95%）；触发拦截时会先存 restore point 并在 Settings → Activity 里让你手动放行。
- 冲突模式：newest-change / 固定偏好某设备 / 手动解决。
- 触发：书签变更（约 1 秒后上传，30 秒兜底）、定时 pull（默认 **60 秒**，可设 30–600 秒；30 秒是浏览器后台定时器下限）、手动。History / open tabs / 扩展列表**只能**走定时间隔。
- 源码佐证（`src/lib/sync/sync-engine.ts:1244-1256`）为防 LWW 乒乓，session payload 被刻意做成确定性：`session.id = \`session_${device_id}\``、`savedAt = ""`、`label = device_label`。还带 `uploadIfChanged` 避免空闲重复提交、PKCE refresh token 解决 ~1 小时 token 过期。

### 6.4 双浏览器

- Chromium（Chrome/Brave/Helium/ungoogled-chromium）：README 原文 **"Fully supported"**，CWS 上架。
- Firefox（含 Waterfox）：**专用构建**上 AMO。README 原文："**Same sync folder and same files as your Chromium browsers**" —— 两边共用同一份同步文件，所以可以 Firefox ↔ Chromium 直接互通。
- 自建：`npm run build` → `dist/`（Chromium）；`npm run build:firefox` → `dist-firefox/`；`npm run checksum` 打印构建指纹。自己编译且用 Drive 后端需要自己的 Google OAuth client；GitHub/WebDAV 只需自己的凭据。

### 6.5 ⚠️ 必须知道的三个扣分项

1. **没有 TSM 那种"多个命名历史会话库"。** 它的 session 就是**每台设备当前打开的标签集合**，每设备只发布最新一份（`RemoteSessionEntry` 按 `device_id` 存）。popup 里是 "Restore sessions (one per peer device)"——每个 peer 一行 + 一个 Restore 按钮（`src/popup/App.tsx:570-596`）。`exportSession(label?)` 虽然支持命名，但自动同步路径写死为设备名，且没有本地多会话保存 UI。ROADMAP 里**也没有**任何"会话库"计划（Next 段是后端扩张 / history 性能 / i18n / reading list / live tab groups；Later 段是 restore-point diff、Filen、OAuth proxy）。
2. **不能导入 TSM 数据。** README/CHANGELOG/ROADMAP 全程无 Tab Session Manager / import / migration 字样。换过去等于从零开始。
3. **太新、用户太少。** repo 2026-05-12 创建，AMO **49 用户 / 0 票**，CWS 7 票。设计和许可证都对，但**成熟度未经检验**。

安全设计（PRIVACY.md，2026-08-07）：无服务器无数据库；只读你开启的数据类型；历史默认 30 天窗口、每次至多 5,000 页；扩展列表只读；已排除 `file://`、浏览器内部页、以及带 `#access_token=` 的 OAuth 回调地址（`tabs-handler.ts` 的 `isSafeContentUrl && !isSensitiveUrl`）。恢复会话有 `MAX_RESTORE_TABS = 200` 硬上限（"the number you were shown is the number you get"）。

## 7 方案 C：floccus（± Tab Stash）——最成熟，但不是会话管理器

<https://github.com/floccusaddon/floccus> · 8,518★ · MPL-2.0 · v5.11.0（2026-09-27，约月更）· AMO 9,673 用户 / 4.47

- 后端最全：Nextcloud Bookmarks、**任意 WebDAV**、Google Drive、Dropbox、Linkwarden、KaraKeep、任意 Git 服务（GitHub/GitLab/Gitea）。[官方 FAQ 确认](https://github.com/floccusaddon/floccus) Nextcloud Bookmarks 与 Git 后端**不能**用 E2EE，只有 WebDAV/Drive/Dropbox 可以。
- 浏览器："known to work in Chrome, Firefox, Edge, Opera, Vivaldi, Brave and Kiwi"（Safari 明确不支持）。
- **和 TSM 的差别**：它同步**书签**，或在一个 profile 里同步**当前打开的标签**——不是 TSM 那种保存会话库的 UI。两个都要就得开两个 sync profile。

⚠️ 官方对 tabs 模式的自我警告（原文）：

> "still slightly experimental as it sometimes causes tabs to duplicate"
>
> "Auto-push can sometimes cause surprises when you have it enabled on multiple devices or when an empty session is pushed after a browser crash, overriding the previously stored session"

—— 安全用法是**手动 push/pull**，别开 auto-push。文档另有两处强调 "Make sure to disable your native browser bookmark sync service, because it is likely incompatible with floccus"。

**Tab Stash**（MPL-2.0，AMO 40,183 用户 / 4.6）把标签批量存成书签组，因此理论上能被 floccus 带走——但注意：README 构建产物列表原文 "`dist-chrome`: A highly-experimental port to Chrome (also unpacked)"，**且没有 Chrome Web Store 上架**，Chrome 侧不可用于生产。**floccus × Tab Stash 这个组合没有任何一方官方文档背书或测试（UNVERIFIED），属架构推断。**

## 8 移动端约束（所有桌面扩展路线都到不了手机）

**Konode 与 NiceTab 都没有移动端，且这不是"没做"，是平台跑不起来。**

一手核实（manifest 层）：

| | Firefox 桌面 | Chromium 桌面 | 移动端 |
|---|---|---|---|
| **Konode** | ✅ | ✅ | ❌ **无** |
| **NiceTab** | ✅ | ✅ + Edge | ❌ **无** |

- **manifest 无 `gecko_android`**（Firefox for Android 的开关就是这个字段）：
  - Konode `scripts/make-firefox-manifest.mjs` 生成的 Firefox manifest，`browser_specific_settings.gecko` 只有 `id: "konabe@proton.me"` / `strict_min_version: "128.0"` / `data_collection_permissions`，**无 `gecko_android`**。
  - NiceTab `wxt.config.ts:46-52`，`browser_specific_settings.gecko` 只有 `data_collection_permissions`，**无 `gecko_android`**（WXT 本身支持 `gecko_android`，此处未配）。
- **AMO `current_version.compatibility` 只列 `firefox`，无 `android` 条目**：Konode `firefox => {min:'128.0'}`、NiceTab `firefox => {min:'58.0'}`。AMO 列表页"适用于 Firefox for Android"徽章由此字段驱动，无 android 条目即桌面限定。
- **构建无 Android 目标**：Konode `package.json` 只有 `build` / `build:firefox` / `package:chrome` / `package:firefox`；NiceTab 只有 `build` / `build:firefox` / `zip` / `zip:firefox`。

**平台硬限制（为什么扩展路线到不了手机）**：

- **Chrome for Android 不支持扩展**（无扩展 API）。
- **Firefox for Android** 支持扩展但有白名单，且 WebExtension API 子集受限，能跑的多是内容拦截器类。
- **iOS**：Safari 扩展是非 WebExtension 另一套；Chrome/Firefox on iOS 都是 WebKit 壳，**不装扩展**。

⇒ 结论：**"Firefox + Chromium 双支持 + 命名会话库 + 移动端"四件事，今天没有任何扩展能同时满足**——这是平台限制，不是产品取舍。

**能到移动端的路线（都不靠 TSM 类扩展）**：

1. **书签路线**：手机浏览器原生书签。但已否决（"不好用、不便于管理"），不采纳。
2. **独立移动 app**（非扩展）：与桌面扩展的会话数据是两套体系，不互通。
3. **只读降级**：会话导出成 Markdown/链接列表，手机上看、手动点开。

> [!note] 需求口径待明确
> **已确认需求口径**：书签同步继续用 floccus（不动）；要解决的是**标签/会话同步**。
> 手机端的期望（可恢复 vs 只读）尚未明确——若需"手机上像桌面一样一键恢复会话"，
> 必须换产品形态（独立 app），需另开调研。

## 10 建议怎么选

```text
你想要"多个命名历史会话库"（= TSM 的核心用法）吗？
├─ 是 → **NiceTab（方案 A，首推）**
│        接受：删除不自动传播，需要时手动 force overwrite 远端；
│              同步后端是 Gists/WebDAV；从 TSM 迁移要手动（不支持 TSM 格式导入）
└─ 否，你要的是"换个设备接着开同一批标签" → Konode（方案 B，次推）
         接受：没有会话库、不能导入 TSM 数据、用户基数极小（49 用户）
         换取：真正的删除感知合并、3+ 设备收敛、可选 E2EE、三个自选后端、

```

**迁移提示**：Konode 与 NiceTab **都不支持导入 TSM 格式**。TSM 侧的导出本身也是半自动的（备份位置被限制在浏览器下载目录内，且没有自动导入）。但 NiceTab 的**导入器支持 5 种格式**（`entrypoints/options/importExport/constants.ts` 的 `formatTypeOptions`：NiceTab / OneTab / KepTab / Toby / Session Buddy），其中 **"NiceTab" 格式 = `TagItem[]` JSON**，可由 TSM JSON 转换得到——见 §11。如果 TSM 里已有大量会话，建议**先别卸 TSM**，用新扩展并行跑一段时间。

## 11 TSM → NiceTab 迁移（转换器已跑通真实数据）

NiceTab 无 TSM 导入器（`extContentImporter` 只有 `oneTab/niceTab/kepTab/toby/sessionBuddy`），但两者的数据结构可确定性映射。已写转换器，并用**真实 TSM 导出**（53 会话 / 1306 标签）端到端跑通（数值见 §13）。

**转换器**：`.research/tsm2nicetab.py`（Python 标准库，无依赖）

```bash
  # 只转手动保存的会话（排除 TSM 自动保存的 regular/winClose/browserExit/temp）
python3 .research/tsm2nicetab.py <TSM导出的.json> --manual-only --category "TSM 手动保存" -o out.json
```

| 参数 | 作用 |
|---|---|
| `--manual-only` | 只保留手动保存会话：排除 tag 含 `regular`/`winClose`/`browserExit`/`temp` 的（这些是 TSM 自动保存，见 §3 的滚动上限，会自己删） |
| `--category NAME` | 把所有会话放进指定 NiceTab 分类名；不给则按 TSM `tag[]` 分组 |
| `-o FILE` | 输出路径；默认 `<input>.nicetab.json` |

**字段映射**（两端源码核对过）：

| TSM（`src/background/save.js:25`） | NiceTab（`entrypoints/types/tabList.ts`） | 说明 |
|---|---|---|
| `name` | `GroupItem.groupName` | **每个 TSM 会话 = 一个标签组**，会话名保留；**同名会话自动追加 ` · YYYY-MM-DD HH:MM`** 以便区分（TSM 里"哔哩哔哩"/"新标签页"会重名） |
| `tag[]` | `TagItem.tagName` | TSM 的 tag 归到 NiceTab 的**分类**；无 tag → `TSM 导入` |
| `date`（ms 时间戳） | `createTime`（`YYYY-MM-DD HH:mm:ss`） | 直接用 NiceTab `newCreateTime()` 的原生格式（`common/utils/common.ts:89` 就是 `dayjs(stamp).format('YYYY-MM-DD HH:mm:ss')`），免得依赖 dayjs 解析 ISO |
| `windows{winId}{tabId}` 各 tab | `GroupItem.tabList` | 按 `tab.index` 升序（**同 TSM `open.js:183` 的排序规则**） |
| tab.`url` / `title` / `favIconUrl` | `TabItem.url` / `title` / `favIconUrl` | — |

**转换时的过滤与规范化**（与 NiceTab 导入逻辑 `importExport.ts:85` 对齐）：

- 丢弃 `about:`/`chrome:`/`edge:`/`brave:`/`file:`/`view-source:`/`devtools:`/扩展页等不可还原标签；
- 丢弃 `data:image/` 内联 favicon（NiceTab 导入时也丢）；
- 跳过空会话。

**实测结果见 §13**。转换器与产物的存放位置（相对仓库根）：

- 转换器：`.research/tsm2nicetab.py`
- 原始导出归档：`.research/src/TMS-<日期>.json`（转换器可直接用它重跑）
- 交付文件：`out/TMS-手动保存22个会话.nicetab.json`

**导入操作**：NiceTab → Dashboard > **Import & Export** → 格式选 **"NiceTab"** → 选生成的 `.json` → **模式选 Append**（勿用 Overwrite，避免清空现有数据）。

Append 模式的落位已从源码确认（`tabListUtils.ts:1637-1660`）：`const newTagList = [stagingAreaTag, ...tags, ...tagList]` —— 导入的分类插在**最前**，现有数据保留在后。

**已知保真度损失**（转换器的取舍）：

- TSM 的 `pinned` / 窗口边界 / 窗口几何 / `windowsInfo` **不保留**——NiceTab 的 `TabItem` 根本没有这些字段（只有 `tabId/title/url/favIconUrl`）。所以 pin 状态和"哪些 tab 属于哪个窗口"会丢失；多窗口会话会被**平铺成一个标签组**。
- 实测数据里多窗口数为 0、pinned 只有 1 个，所以实际损失可忽略。
- 这是 NiceTab 数据模型的硬限制，非转换器缺陷；若需保留 pin/窗口结构，得换 Konode 之类支持多窗口快照的方案。

> [!warning] 转换完请立刻手动导出一次备份
> NiceTab 的同步是 merge 语义（见 §5.3），导入后若直接让自动同步跑，删除不会传播；
> 先落一份本地备份最稳。
